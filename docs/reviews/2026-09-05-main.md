## Major

### 🟠 Apply safe window insets to foreground content, `mobile_controller/app/src/main/java/com/hamzalgh/virtualgamepad/ui/setup/FoundationScreen.kt:35`

**Problem**: `MainActivity` calls `enableEdgeToEdge()`, but the screen's full-window `Column` applies only a fixed 24 dp padding. Neither the activity nor this screen applies system-bar or display-cutout insets. A three-button navigation bar taller than 24 dp covers the bottom text region; a status bar or cutout can likewise exceed the hard-coded top gutter. The supplied phone inventory includes three-button navigation and a cutout, so these are relevant configurations, although no screenshot proving the exact overlap was supplied to this reviewer.

**Why it matters**: The app can obscure its own status/disclaimer text on supported phones. Fixed spacing does not satisfy the repository's safe-inset requirement, and this screen is the starting point for connection UI. Android's [inset guidance](https://developer.android.com/develop/ui/compose/system/insets-ui) explicitly requires content to consume insets after the activity takes over their handling.

**Suggested fix**: Keep the background edge to edge and apply current safe drawing insets to the foreground content before its ordinary design padding. Verify header and footer bounds against the actual safe rectangle in portrait and both landscape directions, including three-button navigation and a display cutout. Exercise the real activity in this check because the existing composable-only test does not establish its window policy.

## Minor

### 🟡 Provide overflow access in constrained windows, `mobile_controller/app/src/main/java/com/hamzalgh/virtualgamepad/ui/setup/FoundationScreen.kt:68`

**Problem**: The screen places all text and the information card in a non-scrollable, bounded `Column`, with weighted spacers around the main content. The spacers can shrink to zero but cannot make the fixed content fit a short window or enlarged font scale. Later children can consequently be constrained or clipped, with no way to reach their full text. The only preview is 412 by 915 dp and the UI test has no constrained-size or font-scale case.

**Why it matters**: The manifest permits rotation, and setup text should remain readable at the user's font size. The reported successful rotation at the phone's current settings does not cover compact windows or large fonts. This is a limited usability issue in the static foundation, rather than a controller-safety defect.

**Suggested fix**: Give the setup content a scroll or adaptive-layout fallback when its natural height exceeds the safe viewport, preserving the spacious arrangement where it fits. Add a compact landscape/large-font verification that confirms all information can be reached without clipping.

### 🟡 Match system-bar icon appearance to the fixed dark theme, `mobile_controller/app/src/main/java/com/hamzalgh/virtualgamepad/app/MainActivity.kt:13`

**Problem**: The no-argument `enableEdgeToEdge()` uses automatic bar styling based on the resources' night-mode configuration, while `VirtualGamepadTheme` always renders a dark background. With Android set to light mode, this selects dark status-bar icons over the app's dark surface and overrides the XML theme's `windowLightStatusBar=false` setting. The automatic policy and its icon assignments are visible in the [AndroidX implementation](https://raw.githubusercontent.com/androidx/androidx/androidx-main/activity/activity/src/main/java/androidx/activity/EdgeToEdge.kt).

**Why it matters**: The status bar can lose readable contrast whenever the phone uses light mode. Neither the supplied evidence nor the composable-only UI test verifies this activity-level configuration.

**Suggested fix**: Explicitly select the dark system-bar style supported by the pinned Activity API, or set the corresponding appearance flags after enabling edge to edge. Check light and dark OS settings and both navigation modes while preserving the app's intended dark theme.
