# Packaging preparation

This directory contains Spec 0010 installer source, signing helpers, notices and review checks. `release-prerequisites.json` records remaining external gates. Neither source nor an unsigned build is release approval. The executable supports terminal mode by default and native tray mode with `--tray`.

From `pc_agent`, inspect a separately built Windows candidate with:

```powershell
.\packaging\inspect-artifact.ps1 -CandidatePath .\target\release\virtual-gamepad-agent.exe
```

The command reads the file, hashes it and reports Windows Authenticode and version metadata. It never runs the candidate, creates keys, signs, changes firewall/startup settings or writes artifacts. `ReleaseApproved` stays false even with a valid signature. Architecture, build provenance, dependency notices, runtime behavior and release gates need separate evidence. Do not publish an unsigned review candidate as an approved release.

`virtual-gamepad.iss` targets Inno Setup 6.7.3. The compiler is not distributed with the product. The user authorized its acquisition and portable installation for review compilation. The official is-6_7_3 distribution SHA-256 is `9C73C3BAE7ED48D44112A0F48E66742C00090BDB5BEF71D9D3C056C66E97B732`; the downloaded signature validated as Pyrsys B.V. Its extracted ISCC.exe SHA-256 is `0A8757031B33777E4C9CBFFEE40F11A5062B36D25CBE144C1DB73B6102B80AD7`. Upstream /PORTABLE=1 /CURRENTUSER mode keeps this build tool in ignored target/packaging-tools, without shortcuts, associations or uninstall registration. Verify origin before trusting any future compiler copy. ISCC's PE version is 0.0.0.0, so the script enforces `Ver == 0x06070300` in addition to the supplied compiler hash. The pinned license permits use including commercial applications; retain upstream notices. The compiler banner's non-commercial reminder is recorded separately from those license terms.

The installer never bundles or runs ViGEm setup. Its unchecked firewall task permits only the installed executable, UDP 8765, Private profile and LocalSubnet. A custom runtime port needs an explicitly authorized change to that exact rule. Startup is off by default and belongs to the ordinary user runtime. Setup waits for application exit and never force kills. Optional postinstall startup waits up to 120 seconds for setup itself to close before opening the service.

Uninstall preserves data by default. Optional deletion names the account running the elevated uninstaller and its exact LocalAppData directory. Other accounts' data and startup entries are preserved; disable startup from those accounts before removing the application. An entry belonging to a different executable path is never removed. Existing driver installation is always preserved.

Run `check-packaging.ps1` for PowerShell syntax and mocked ownership/error scenarios. It cannot validate Inno compilation, elevation, Windows Firewall, registry permissions or real uninstall behavior.

For a review package, build the release executable and stage it with root LICENSE, NOTICE, this directory's THIRD_PARTY_NOTICES.txt and troubleshooting.txt. The resource build uses the installed Windows SDK rc.exe (or explicitly selected VG_RC_EXE) to embed version information and an asInvoker manifest. Example compilation, after compiler verification:

```powershell
.\packaging\build-package.ps1 -Compiler 'VERIFIED_ISCC_PATH' -CompilerSha256 'VERIFIED_ISCC_SHA256' -Stage 'REVIEW_STAGE_PATH'
```

For an official candidate, use an existing approved certificate with `sign-artifact.ps1` to sign the staged executable first. Pass its thumbprint to `build-package.ps1 -Official -CertificateThumbprint ...`, then sign the produced installer and verify it with the same helper. The helper requires a provider-approved HTTPS timestamp service, verifies signature/signer/timestamp, and computes SHA-256 only after signing. No helper creates a key, publishes an artifact or purchases a certificate. No automatic updater exists. A signed candidate still needs manual release acceptance.

Android uses its independent Gradle project. `gradlew.bat assembleRelease --offline` creates an unsigned review APK. For authorized official signing, provide VG_ANDROID_KEYSTORE, VG_ANDROID_STORE_PASSWORD, VG_ANDROID_KEY_ALIAS and VG_ANDROID_KEY_PASSWORD only in the release owner's environment, then run `gradlew.bat assembleRelease -PofficialRelease=true --no-configuration-cache`. Keep the keystore outside the entire repository. Missing values fail immediately. `verify-apk.ps1 -ApkSigner ... -Apk ... -ExpectedCertificateSha256 ...` rejects unsigned APKs, the standard Android debug identity and an unexpected signer. Signature continuity, physical install and upgrade remain external checks. An APK signed with a new release identity cannot upgrade an existing debug-signed install; preserve that install until a deliberate migration is chosen. Do not uninstall it just to make a check pass.

The provisional user-authorized credit is **Virtual Gamepad contributors**. Apache 2.0 LICENSE/NOTICE and third-party notice files are prepared. To refresh notices after dependency changes, export Windows-filtered `cargo metadata --locked --offline --format-version 1` and Android `gradlew.bat exportReleaseDependencyInventory --offline --no-configuration-cache`, then run `prepare-notices.ps1` with those generated paths and the verified upstream protobuf license text. The notice review covers the locked Windows graph and Android resolved release artifacts; every dependency change requires review. Android assets carry license/notice text. Final publication identity and redistribution review remain separate from this preparation.

The governing details, consolidated manual checklist and acceptance gates are in [Spec 0010](../../docs/specs/0010-desktop-tray-and-packaging.md). Existing accepted phone checks remain accepted; this packaging work does not restart gameplay or reliability campaigns.

## Remaining manual checks for the compiled review installer

In the firewall GUI, the owned rule is displayed as **Virtual Gamepad private UDP**; `VirtualGamepad.Desktop.UDP` is its internal Name. Similar **Virtual Gamepad desktop agent** entries can belong to Windows prompts for other executable paths. Inspect each rule's program and scope before changing it. A correct owned rule does not narrow additional broad Allow rules for the same program.

Current deliverables are `dist/preview/windows/VirtualGamepad-Windows-Setup-Preview.exe` and `dist/preview/android/VirtualGamepad-Android-Preview.apk`, with hashes and plain installation notes in `dist/preview`. The Windows installer remains unsigned. The Android release payload is signed with the existing development certificate for local preview only; official-release signing guards remain unchanged. The user reports basic install/reinstall/uninstall success; the detailed scenarios below remain reference gates, not a request to repeat that long checklist. The old Spec 0010 review folders and isolated build caches were removed at the user's request. No app or phone campaign was run during packaging.

1. **Installation and cancellation.** Exit the current tray normally and wait for it to disappear; check Task Manager for remaining virtual-gamepad-agent processes. Disable startup from the old portable path first if it is enabled. Open the review installer from File Explorer. Setup elevation is expected, unlike runtime elevation. Cancel once before Install: no app installation or owned firewall rule should appear. Reopen, retain the default destination and leave both the firewall task and final launch unchecked for the first installation. Verify installed files, notices and shortcuts, with no driver installation. Existing per-user settings and pairing metadata must remain intact.
2. **Exact firewall consent and installed launch.** Reopen setup and explicitly select its Private UDP task. Finish with launch unchecked. In Windows Defender Firewall with Advanced Security, inspect inbound rule VirtualGamepad.Desktop.UDP: exact installed executable, UDP 8765, Private only, remote LocalSubnet. Public must remain unallowed. Existing unrelated rules must remain unchanged. Existing broader manual rules are not automatically removed; record them as unresolved scope if present. Start the installed Start-menu shortcut as an ordinary user: one icon, normal settings, and no runtime UAC request. If a firewall warning remains, capture it before changing rules. The installed path's first connection needs a fresh code and a freshly checked Wi-Fi IPv4; this is setup reachability evidence, not another gameplay campaign.
3. **Running protection and cancelled uninstall.** With the installed tray running, reopen setup and request uninstall separately: both must refuse until a normal Exit completes, without force termination. After Exit, open uninstall again and cancel its normal confirmation: app files, settings, startup and firewall entries must remain intact. The separate data-deletion question must not appear before confirming uninstall.
4. **Reinstall, then uninstall preserving data.** Run the same installer again after Exit; confirm settings survive. This proves reinstall only, not upgrade between versions. Uninstall, confirm the operation, then choose No for removal of settings/pairings/logs. Verify owned program files/shortcuts, the exact owned firewall rule and matching startup entry are removed, while per-user data, unrelated rules and the shared ViGEm driver remain. Reinstall and confirm settings return and a fresh code is still required.
5. **Separate disposable-machine checks.** Explicit Yes for data removal belongs on a disposable Windows account or VM containing no valuable pairing/settings records. Verify deletion only of the account/path shown, preservation of other accounts and foreign startup/rule entries, and refusal when ownership cannot be verified. Cover Windows 10 and Windows 11 x64, driver absent and present without removing a working shared driver. Verify the optional final launch starts only after setup closes. Check a real version-to-version upgrade when a second approved version exists; repeated installation of 0.1.0 is not that evidence.
6. **Signing and Android release gates, pending credentials.** Verify the expected Windows runtime/installer signer and timestamp, final hashes, and the APK release certificate and non-debuggable flag. Use authorized fresh installs and upgrades with the same release key on Android, preserving settings. Do not uninstall the debug-signed phone app to force an upgrade test. Signing credentials, official publication identity and broader reliability/platform acceptance remain pending.

Report each applicable item as passed, failed with the exact message, or pending with its reason. These checks do not authorize automatic app launches, device input, signing, publication or driver changes by an agent.
